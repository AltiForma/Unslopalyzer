# UN004: Extract multi-line condition into a named variable

Flags `if`, `while`, `do-while` and ternary conditions made of a single operand that wraps across lines, such as a method call with its arguments split over several lines.

| Property             | Value                                               |
|----------------------|-----------------------------------------------------|
| Rule ID              | UN004                                               |
| Title                | Extract multi-line condition into a named variable  |
| Category             | Readability                                         |
| Default severity     | Warning                                             |
| Enabled by default   | Yes                                                 |
| Code fix available   | No                                                  |

## Rationale

Coding agents often call a method with several arguments directly inside an `if`. Once the formatter wraps the arguments, the branch's meaning is buried in an argument list: the reader has to scan past every argument, and then back to a `!` at the start, to work out when the branch runs.

Assigning the result to a local whose name states what it means turns the condition into a single readable word, and puts the call where it can be read on its own.

## When it reports

A condition is reported when **both** of these are true:

1. It has exactly **one** operand, counted the same way as [UN001](UN001.md#how-operands-are-counted). A negated call, a comparison, an `is` pattern or a single lambda call all count as one.
2. The condition itself, meaning the text between `if (` and `)`, spans more than one line.

A condition whose parentheses sit on their own lines, while the expression between them fits on one line, is not reported.

Conditions with two or more operands are UN001's job, so the two rules never report the same condition.

Like UN001's line-break trigger, this depends on how your code is formatted. With CSharpier, a call wraps once it no longer fits on one line.

## Examples

### Non-compliant

```csharp
if (
    !await licensing.IsActivationValidAsync(
        customerId,
        productKey,
        machineFingerprint,
        cancellationToken
    )
)
    return Forbid();
```

```csharp
if (
    shipments.Any(shipment =>
        shipment.IsDelayed && shipment.DaysLate > 3
    )
)
    await escalation.NotifyAsync(cancellationToken);
```

### Compliant

```csharp
var activationIsValid = await licensing.IsActivationValidAsync(
    customerId,
    productKey,
    machineFingerprint,
    cancellationToken
);

if (!activationIsValid)
    return Forbid();
```

```csharp
var hasSeriouslyDelayedShipment = shipments.Any(shipment =>
    shipment.IsDelayed && shipment.DaysLate > 3
);

if (hasSeriouslyDelayedShipment)
    await escalation.NotifyAsync(cancellationToken);
```

Name the variable after the positive fact (`activationIsValid`) and keep the `!` in the `if`. That reads more naturally than a name like `activationIsInvalid`.

## Known limitations

- Only `if`, `else if`, `while`, `do-while` and ternary conditions are checked. Wrapped expressions in `return` statements, assignments and arguments are not.
- There is no code fix by design. The value of the rule is a name that explains the intent, which a tool cannot choose.
