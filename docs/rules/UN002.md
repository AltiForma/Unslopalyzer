# UN002: Avoid needless ThrowIfCancellationRequested calls

Flags `CancellationToken.ThrowIfCancellationRequested()` calls that are not inside a loop.

| Property             | Value                                               |
|----------------------|-----------------------------------------------------|
| Rule ID              | UN002                                               |
| Title                | Avoid needless ThrowIfCancellationRequested calls   |
| Category             | Redundancy                                          |
| Default severity     | Warning                                             |
| Enabled by default   | Yes                                                 |
| Code fix available   | No                                                  |

## Rationale

Coding agents sprinkle `cancellationToken.ThrowIfCancellationRequested();` throughout async code: at the top of methods, between awaits and before returns. The cancellable operations the token is passed to already observe it and throw `OperationCanceledException` when it fires. An extra check moments before or after one of those calls almost never makes the code respond to cancellation any sooner. It only adds noise.

Cancellation is best supported by passing the token to every operation that accepts one.

The one place a manual check pays off is inside a loop doing work that never sees the token, such as CPU-bound processing of a large collection. Calls inside `for`, `foreach`, `await foreach`, `while` and `do-while` bodies are therefore allowed, including calls nested in an `if` within the loop body.

## Examples

### Non-compliant

```csharp
public async Task<Invoice?> ApproveAsync(int id, CancellationToken cancellationToken)
{
    cancellationToken.ThrowIfCancellationRequested();

    var invoice = await repository.FindAsync(id, cancellationToken);
    if (invoice is null)
        return null;

    cancellationToken.ThrowIfCancellationRequested();

    await repository.SaveAsync(invoice, cancellationToken);
    return invoice;
}
```

### Compliant

```csharp
public async Task<Invoice?> ApproveAsync(int id, CancellationToken cancellationToken)
{
    var invoice = await repository.FindAsync(id, cancellationToken);
    if (invoice is null)
        return null;

    await repository.SaveAsync(invoice, cancellationToken);
    return invoice;
}
```

A check inside a loop of CPU-bound work is allowed:

```csharp
foreach (var row in matrix)
{
    cancellationToken.ThrowIfCancellationRequested();
    total += row.Sum();
}
```

## Known limitations

- The loop exemption is purely syntactic. A loop whose body only awaits cancellable calls is still exempt, even though the check is redundant there too.
- A call inside a lambda or local function is judged by that function's own body. A lambda declared inside a loop is not exempt unless the call is also inside a loop within the lambda.
- Only `System.Threading.CancellationToken.ThrowIfCancellationRequested` is flagged. Methods with the same name on other types are ignored.
- There is no code fix. Removing the call is easy, but whether the token is passed on to the right operations needs a human to check.
